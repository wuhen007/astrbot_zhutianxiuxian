# 原版对齐路线图

> 基准：原版固定快照 `04af6a9a7ec11e700a0aedb85a5981e48826035c`（`gitee.com/mo-wuming/zhutianxiuxian1.0`）
> 现状基线（2026-11-27 核对）：指令缺口 306 条 / 整块缺口 24 个 / 行为不一致 13 类 / 数据表差异 1 条
> 数据层已 1:1（148 张表、22 张重点表 0 处数值偏差），后续工作全部在**逻辑、入口与交互**层。

## 一、对齐原则

1. **数据不动，只对行为**。表已一致，不要为了"像原版"改数值；数值差异一律以原版 JSON 为准，发现不一致先查表再改代码。
2. **一块一提交**。每个玩法单独 commit（能单独回滚），commit 里写明对应的原版文件与行号。
3. **先写对照测试再实现**。每块至少 1 条规则测试 + 1 条边界测试，测试命名带原版模块名，便于反查。
4. **迁移只增不改**。`LATEST_DB_VERSION` 只能往上加，历史迁移函数不改；跨版本升级路径要有测试。
5. **不做"看起来像"的实现**。入口存在但走不通、帮助页宣传但没逻辑，必须标为未实现而不是半成品。

## 三、工作流

```
选一块 → 读原版对应文件（记行号）→ 写对照测试（红）
      → 实现 → 本地 unittest + selfcheck → commit（一块一提交）
      → 推送 codex 分支 → 实机验证 → 合 main
```

1. **固定快照**：始终用 `04af6a9`，不要跟着原版 HEAD 走，避免边对齐边移动靶子；换快照单独一批做。
2. **差异基线脚本化**：把 `audit/` 里的 `cmd_diff.py`、`table_diff.py`、`classify2.py` 收进 `tools/parity/`，发版前跑一次，缺口数写进 CHANGELOG。
3. **测试门禁**：`python -m unittest discover -s tests` + `python tests/selfcheck.py` + `python tests/verify_data.py`，三条全绿才推。
4. **帮助页同步**：新增入口必须同时改 `data/help/*.json`，否则视为未完成。
5. **存档兼容**：涉及新表或字段时，补一条「旧版本 → 新版本」迁移测试。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 战斗规则改动导致战力普降，玩家反弹 | 一次性改完 + 公告 + 按境界补修为；不要分多次偷偷改 |
| 对轰/行动条属结构改造 | 开关式灰度，保留旧路径一个版本 |
| 迁移分叉（v19 已出现一次） | 迁移编号由 main 决定，分支不得自行插号；升级脚本加版本单调断言 |
| 分支与本地再次漂移 | 每完成一块立即推分支，本地不再作为唯一真源 |
| 原版数据看似一致但字段语义不同 | 以「同名字段 + 同种子对照测试」为准，不靠肉眼比对 |
