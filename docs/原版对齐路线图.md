> 基准：原版固定快照 `04af6a9a7ec11e700a0aedb85a5981e48826035c`（`gitee.com/mo-wuming/zhutianxiuxian1.0`）
> 目标：**除跨服外，原版每个可玩功能在本地都有等价入口且规则一致**；命令名兼容；数据与数值一致。
> 现状基线（2026-11-27 分诊后）：**待实现 443 条**（P2 31 / P3 96 / P4 77 / P5 239）、可补别名 168 条、碎片 46 条、跳过 5 条；整块缺口 24 个、行为不一致 13 类、数据表差异 1 条。
> 分诊明细见 `tools/parity/triage.csv`（662 条逐条判定：原版命令 / 文件 / 行号 / reg 原文 / 本地承接 / 判定 / 阶段）。

## 一、对齐的定义与边界

"完全对齐"指**功能等价**，不是**字节级一致**。以下四类不做 1:1：

| 类别 | 具体项 | 处理方式 |
|---|---|---|
| 跨服（按要求排除） | worldChat、channels、web-gateway、跨服交易、跨服无尽/团本、总机/区服/频道 | 不移植，帮助页不出现 |
| 原版缺陷 | `data.jineng` 十技能无定义体（切磋因此必崩）、`biwu.js` 减攻/减防永久累乘、往生无裁定入口 | 对齐**意图**，修掉缺陷并注明差异 |
| 宿主能力差异 | 云崽的 redis 多轮会话、私聊推送、Web 网关；本地方案为 AstrBot 事件 + SQLite | 交互形态可不同，玩法结果必须一致 |
| 呈现层 | 图片面板的像素布局、字体、配色 | 信息项对齐即可，不追求视觉一致 |

另外三类属于**运营/内容**，按需执行，不影响功能完整性：周年活动、调研问卷、商人楼促销。

## 二、对齐原则

1. **数据不动，只对行为**。148 张表已 1:1，数值差异一律以原版 JSON 为准；发现不一致先查表再改代码。
2. **一块一提交**。每个玩法单独 commit，提交信息写明对应原版文件与行号，便于反查与回滚。
3. **先写对照测试再实现**。每块至少 1 条规则测试 + 1 条边界测试，测试名带原版模块名。
4. **迁移只增不改**。`LATEST_DB_VERSION` 只往上加，历史迁移不改；跨版本升级要有测试。
5. **不做"看起来像"的实现**。入口在但走不通、帮助页宣传但没逻辑，一律标未实现，不留半成品。
6. **原版命令名必须可用**。改名可以，但原版写法要保留为别名，避免老玩家与攻略失效。

## 四、工作流

```
分诊条目 → 读原版对应文件（记行号）→ 写对照测试（红）
        → 实现 → unittest + selfcheck + verify_data → commit（一块一提交）
        → 推 codex 分支 → 实机验证 → 合 main
```

1. **固定快照**：始终用 `04af6a9`，不跟原版 HEAD，避免边对齐边移动靶子。
2. **差异脚本进仓库**：`audit/` 的 5 个脚本收进 `tools/parity/`，每个 Phase 结束跑一次，缺口数写进 CHANGELOG。
3. **测试门禁**：`unittest discover` + `selfcheck.py` + `verify_data.py` 三条全绿才推。
4. **别名优先**：实现新玩法时同时注册原版命令名，减少后续兼容成本。

## 六、工期与风险

单人、每天 4~6 小时有效开发估算：**约 3.5~4.5 个月**（0 止血 + 0.5 分诊已完成；1 战斗 5 天 + 2 接线 31 条约 1 周 + 3 高频 96 条约 4 周 + 4 长线 77 条约 6 周 + 5 剩余 239 条约 5 周 + 6 验收 2 周）。

| 风险 | 对策 |
|---|---|
| 分诊后工作量翻倍 | 先做 Phase 0.5，按真实清单排期，不按旧数字承诺 |
| 战斗改动导致战力普降 | 一次性改完 + 公告 + 按境界补修为，不分多次偷改 |
| 对轰/行动条属结构改造 | 开关式灰度，保留旧路径一个版本 |
| 迁移分叉（v19 已出现一次） | 编号由 main 决定，分支不得插号；升级脚本加版本单调断言 |
| 分支与本地再次漂移 | 每完成一块立即推分支；本地改为 git 工作副本 |
| 原版命令名与本地重名 | 别名注册时检测冲突，冲突项在分诊表登记 |
